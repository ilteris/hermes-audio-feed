Marcus: Now let's dive into Module 2: The Core Technical Architecture. Mindy asks: 'When designing a core component consumed by forty-plus vertical teams—Shopping, Maps, Knowledge Graph, AI Overviews—how do you draw the architectural boundary between component-internal state and consumer-controlled state?'
Alex: This is the classic design system scaling dilemma. If you try to anticipate every vertical's feature request with configuration props, you end up with sixty-prop monoliths like showPriceBadge, showFlightDuration, showDistanceMarker. The component becomes impossible to test, impossible to tree-shake, and breaks constantly.
Marcus: His answer established Inversion of Control through a rigorous 3-Layer Framework.
Alex: Layer 1 is Internal Interaction Mechanics. This covers hover states, active focus rings, keyboard navigation index, and ARIA attributes like aria-expanded and aria-activedescendant. The design system owns one hundred percent of this layer. Consumer teams cannot override or bypass it. That is how keyboard accessibility and WCAG compliance remain unbroken across forty different product verticals.
Marcus: Layer 2 is the State Contract, implemented as a hybrid controlled-uncontrolled pattern. If a simple prototype or lightweight vertical just wants a filter chip, they pass defaultValue, and the component manages its own toggle state internally.
Alex: But if a high-stakes vertical like Google Shopping or Google Flights consumes that chip, the state must synchronize with URL query parameters and browser history navigation. In that mode, the consumer passes value and onChange. The component yields internal state management and acts as a pure, deterministic renderer.
Marcus: And Layer 3 is Composition over Configuration using compound components and slots. The design system provides the layout grid, spacing tokens, and focus boundaries. The vertical team injects their domain-specific UI into designated slots—like SearchCard.Header, SearchCard.Media, and SearchCard.Actions.

Alex: And here was the most critical senior insight of the entire drill: Ilteris grounded this directly in Google Search's actual runtime stack. Search does not run on React!
Marcus: That is a massive point. If you start talking about React hooks, virtual DOM reconciliation, and Next.js hydration in a Search interview, you immediately lose credibility. React's runtime overhead would obliterate Search's latency budgets.
Alex: Search runs on Wiz, Closure, Soy templates, JSAction, and increasingly Web Components.
Marcus: And Ilteris mapped the three layers directly to Wiz primitives. Layer 1 uses jsaction for declarative event delegation—no JavaScript event listeners are hydrated until the user actually interacts. Layer 2 treats the URL query string as the single source of truth. And Layer 3 uses Soy template transclusion and native browser slot elements. That demonstrates authentic platform engineering literacy.

Alex: That leads naturally into Module 3: Performance under Strict Search Latency Budgets and Core Web Vitals.
Marcus: Every millisecond of delay on the SERP directly impacts user engagement and query volume. With AI Overviews streaming generative tokens into the page, maintaining Largest Contentful Paint, Cumulative Layout Shift, and Interaction to Next Paint is an engineering minefield.
Alex: How does his architecture defend against those regressions?
Marcus: First: Zero-JS Token Delivery. Runtime CSS-in-JS is strictly banned. Design tokens compile at build time into pure CSS custom properties scoped to container classes. When switching between light mode, dark mode, or high-contrast, the browser resolves the styles in its native C++ cascade engine by toggling a root class. There is zero JavaScript execution and zero style recalculation on the main thread.
Alex: Second: Eliminating Cumulative Layout Shift for AI Overviews. When Gemini or an LLM streams tokens onto the page, text expands line by line. If unconstrained, it pushes organic search results down the screen, causing massive CLS penalties.
Marcus: His defense uses strict CSS containment: contain layout size on dynamic card containers. This informs the browser rendering engine that internal DOM mutations or streaming text inside the card will not alter the geometry of the surrounding search page.
Alex: In addition, they enforce pre-allocated geometric envelopes with explicit aspect-ratio boxes and min-height placeholders based on query classification metadata. Text streams into a bounded viewport with line clamping and an explicit expansion affordance.
Marcus: And third: Protecting Interaction to Next Paint. The design system strictly forbids animating geometry properties like height, width, top, or margin. All layout state transitions must use compositor-only properties: transform and opacity. And design system primitives enforce batched DOM reads and writes to eliminate layout thrashing.

Alex: Module 4 tackles the 4-Phase Component Graduation Pipeline and Governance. Mindy asks: 'If dozens of vertical teams are inventing new UI patterns, how do you prevent the design system team from becoming a bottleneck while keeping the core library clean?'
Marcus: Ilteris introduced the Rule of Three. A new UI pattern does not enter the core design system on day one. It must be needed by at least three distinct verticals—for example Shopping, Maps, and AI Overviews.
Alex: The pipeline has four concrete phases. Phase 1 is Incubation in User Space. The vertical team builds the pattern inside their own codebase or inside a design-system slot. They move fast and validate user value without filing tickets.
Marcus: Phase 2 is Decoupling and API Architecture. A design system engineer pairs with the feature team to strip domain-specific models like ProductPricePayload into generic presentation slots, normalize raw hex colors into semantic tokens, and invert state control.
Alex: Phase 3 is The System Gate. This is the non-negotiable verification checkpoint: WCAG 2.2 accessibility audits, keyboard focus traps, performance budgets, CSS containment verification, and internationalization with CSS logical properties tested against forty percent text expansion in German or Finnish.
Marcus: And Phase 4 is Staged Promotion with Codemods. The component rolls out under an experimental tag for canary verification, graduates to core, and an automated Abstract Syntax Tree codemod automatically migrates legacy imports across vertical codebases.

Alex: Module 5 is the Live Coding Breakdown: building an accessible autocomplete typeahead.
Marcus: This is the classic Google VIP coding prompt. Ilteris walked through four vital production requirements before writing code.
Alex: First, asynchronous concurrency. When users type rapidly, network responses return out of order. He combined a 150-millisecond debounce with an AbortController signal, ensuring older in-flight fetches are cleanly aborted before new requests trigger.
Marcus: Second, the WAI-ARIA 1.2 Combobox pattern. The input maintains role combobox, aria-expanded, aria-controls, and aria-activedescendant. Physical DOM focus remains locked inside the text input so the user can continue typing, while virtual focus moves through the option list.
Alex: Third, the critical mousedown versus click event timing. In the browser event lifecycle, mousedown fires before blur. If you attach a click listener to dropdown options, the input blurs and collapses the listbox before the click can register. Adding e.preventDefault on mousedown preserves input focus while successfully capturing the selection.
Marcus: And fourth, Input Method Editor composition handling. For international users typing in Japanese, Chinese, or Korean, characters are composed phonetically. Pressing Enter confirms a candidate kanji or hanzi character. Checking event.isComposing prevents that confirmation keypress from accidentally submitting the search query.
